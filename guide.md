# Operations & Integration Guide: `@xoisr/html-cache`

`@xoisr/html-cache` enables Nginx to directly serve pre-rendered HTML files generated by your application. Requests without existing cache files proxy once to Node. Cache files are created only when the application explicitly calls `warm()`.

Designed for single-site, single-machine setups on local disk using standard Nginx OSS. The package has no admin UI, no Redis, no database, and does not automatically store the response of every MISS.

Install the package and copy the four integration files from [README.md](README.md) into your app. API signatures are documented in [api.md](api.md). This guide covers deployment, Nginx configuration, operations, and zero-downtime cutover. The complete behavioral specification is documented in [docs.md](docs.md).

## 1. Prerequisites

- Node.js 22 or later. The npm package distributes ESM JavaScript with TypeScript declarations.
- Nginx OSS compiled with `gzip_static`. The generated snippet is `include`d inside the virtual host serving `publicUrl`.
- Production app running with `next start` or `node server.js` (when using Next.js `output: 'standalone'`).
- `next.config` configured with `trailingSlash: false` and `deploymentId` matching `storage.releaseId`. Next binds `deploymentId` at `next build` time, so this variable must be set during build.
- File permissions: Nginx process user must have read access to `<cache>/<releaseId>`. Node process user must have read and write access to the cache directory and its `control/` directory.

> `next dev`, Edge runtime, and serverless environments do not write cache files. `createCache()` only initializes an in-memory object; filesystem state, cron, and Nginx configurations only change when invoking specific action methods.

## 2. Installation & Setup

```bash
npm install @xoisr/html-cache
```

In `next.config.mjs`:

```js
const nextConfig = {
  trailingSlash: false,
  deploymentId: process.env.CACHE_RELEASE_ID,
};

export default nextConfig;
```

Next.js imports the package directly without requiring `transpilePackages`. `node-cron` is an optional dependency for `startCron()`. If `node-cron` is not installed, the internal scheduler falls back to a 60-second `setInterval`.

## 3. HTML Page Markers

Every page that is eligible for caching must emit two markers reflecting the rendered content:

| Marker | Source |
|---|---|
| Release | `data-dpl-id` attribute on `<html>` (injected automatically by Next.js from `deploymentId`), or `<meta name="hiden-cache-release">` |
| Revision | `<meta name="hiden-cache-revision">` |

```tsx
export async function generateMetadata(): Promise<Metadata> {
  const article = await getPublishedArticle();
  return {
    other: {
      'hiden-cache-revision': article.revision,
    },
  };
}
```

The revision is an exact string comparison value, e.g. `article-123:v42`. The homepage and category listing pages emit their own distinct revision strings. `commitVersion` is a strictly increasing integer assigned by the CMS per URL (different URLs do not share the same version counter).

A cacheable response must return HTTP `200`, `text/html`, without `Set-Cookie`, and without `private`, `no-store`, or `no-cache` directives. Pages or layouts calling `cookies()`, `headers()`, `draftMode()`, `connection()`, or reading dynamic `searchParams` cause Next.js to emit `no-store`. The internal validator rejects such responses, preventing cache file generation.

For pagination, encode the page number into the URL path (e.g. `/news/economy/page/2`). That path functions as a standard cacheable URL. Query variants like `?page=1` are only cached when every query value's response passes full validation.

Routes where middleware enforces login, redirects, A/B experiments, or emits `Set-Cookie` must be placed in `exclude`. Middleware does not run on cache HITs.

## 4. Cache Configuration

```ts
import { createCache } from '@xoisr/html-cache';

export const cache = createCache({
  origin: {
    internalUrl: 'http://127.0.0.1:3000',
    publicUrl: 'https://news.example.com',
    basePath: '',
    staticRoot: '/var/www/news/current/.next/static',
    previousStaticRoot: '/var/www/news/previous/.next/static',
  },
  storage: {
    directory: '/var/cache/hiden',
    releaseId: process.env.CACHE_RELEASE_ID!,
  },
  policy: {
    include: ['/', '/news/**', '/categories/**'],
    exclude: ['/admin/**', '/booking/**'],
    trailingSlash: 'never',
    query: {
      allow: {
        page: { type: 'digits' },
      },
    },
    cookies: { mode: 'allowlist', harmless: [] },
  },
  document: {
    cacheControl: 'private, no-store',
    compression: 'nginx',
  },
  ttl: { seconds: 3600, enforcement: 'cron-soft' },
  cron: { enabled: true },
});
```

- `internalUrl`: Internal TCP loopback address of the Node process serving this release. `warm()` forwards `Host` matching `publicUrl`.
- `releaseId`: Alphanumeric string (with `.`, `_`, or `-`, up to 64 characters) matching the HTML release marker.
- `include`: Paths to cache. If empty, no URLs are cached.
- `exclude`: Always takes precedence over `include`. Built-in excludes always filter `/.well-known/**`, `${basePath}/_next/**`, and `${basePath}/api/**`.
- Wildcards: `/news/**` matches `/news` and all sub-paths. `/news/*` matches exactly one segment. `**` can only appear at the end of a pattern.
- Query allowlist: Maximum 3 parameter names matching `^[a-z][a-z0-9_]{0,31}$`. `digits` accepts `1` to `999999` (e.g. `page=1` is accepted, `page=0` or `page=01` is rejected). `enum` accepts `[a-z0-9_-]{1,32}`. Unknown parameters bypass the cache completely (parameters are not stripped).
- Cookies: In v0.1, `cookies.harmless` must remain `[]`. Any cookie or `Authorization` header triggers cache bypass.
- `staticRoot`: Path to `_next/static` for the current release. Specifying `previousStaticRoot` ensures existing browser tabs can still download previous chunk assets. If both are omitted, `/_next/static/` proxies to Node.
- Compression: `compression: 'nginx'` pre-compresses and writes `index.html.gz` alongside `index.html`. `compression: 'off'` only saves raw HTML.
- `createCache()` throws `ConfigError` if rules cannot be expressed natively in Nginx OSS.

## 5. One-Time Initialization

Invoke `init()` once when the production Node process launches. Do not call it on per-request lifecycles:

```ts
// instrumentation.ts
export async function register() {
  if (process.env.NEXT_RUNTIME !== 'nodejs') return;
  if (process.env.NEXT_PHASE === 'phase-production-build') return;
  if (process.env.NODE_ENV !== 'production') return;
  const { getCache } = await import('./app/cache');
  const cache = getCache();
  await cache.init();
  cache.startCron();
}
```

On first startup, if `control/serving-release` is not present, `init()` registers the current release as the active serving release. Later releases do not overwrite this file during `init()`. Switching active serving release occurs via `activateServing()` after Nginx reload.

## 6. Nginx Integration

The generated configuration is a location snippet. Include it inside the virtual host serving `publicUrl`:

```ts
await getCache().writeCutoverConfig('/etc/nginx/snippets/hiden-html-cache.conf');
```

In your Nginx site configuration:

```nginx
server {
    listen 443 ssl;
    server_name news.example.com;

    include /etc/nginx/snippets/hiden-html-cache.conf;
}
```

`writeCutoverConfig` validates the staged tree and rejects if the generation contains files older than a purge event, has open purge intents, or has mismatched `meta.releaseId`. Empty generations are valid. Run `nginx -t` and reload Nginx. The include file binds both cache `root` and upstream `proxy_pass` to the same release.

Location evaluation order in the generated snippet:
1. `/.well-known/`
2. `/_next/static/` (using `^~` to override generic regex rules like `.js|.css`)
3. `/_next/image` and `/_next/data/`
4. `/api/` and excluded directory prefixes (proxied as-is without document caching headers)
5. Document HTML: HIT when file exists, MISS when eligible without file, BYPASS when policy dictates

Creating `control/maintenance` causes all document requests to BYPASS cache. Deleting that file restores HIT serving without reloading Nginx.

## 7. Warming Cache

```ts
await cache.warm('/news/article-a', {
  expectedRevision: 'article-123:v42',
  commitVersion: 42,
});
```

`warm()` sends a GET request to `internalUrl` without cookies. Origin must return HTML matching the target release and expected revision. Subsequent calls with identical revision and version while the file is intact are idempotent and skip re-fetching.

When a version floor exists, warming without `expectedRevision` throws `REVISION_REQUIRED`. A mismatching revision throws `REVISION_MISMATCH`. A smaller `commitVersion` throws `STALE_EVENT`. Same version with a different revision throws `VERSION_CONFLICT`.

Unwarmed URLs continue proxying to Node. A warming error does not invalidate existing cache files unless a preceding `purge()` already cleared them.

`warmMany(['/', '/news/article-a'])` warms URLs without revisions, valid only when the target URL has no prior revision floor.

## 8. Publishing After Commit

Execute after the CMS transaction has successfully committed to the database:

```ts
import { getCache } from '../../cache';

await getCache().publishDocument({
  url: '/news/article-a',
  minRevision: 'article-123:v42',
  commitVersion: 42,
  revalidate: async () => {
    revalidatePath('/news/article-a');
  },
});
```

`publishDocument()` executes in strict order:
1. Purges the target cache files and sets revision floor.
2. Runs `revalidate()` (e.g. Next.js `revalidatePath()`).
3. Warms the new HTML file with expected revision.

| Event | Recommended Action |
|---|---|
| Create or update article | Publish article URL with article revision, and listing page with listing revision |
| Slug changed | Purge old slug and new slug, then warm new slug |
| Deleted or set to draft | Purge public URL and related listing |
| Global header / footer update | Purge individual pages, or invoke `purgeAll()` |

## 9. Purging Cache

```ts
await cache.purge('/news/article-a', {
  minRevision: 'article-123:v42',
  commitVersion: 42,
});
```

- `purge()` removes files across all releases on disk and advances the revision floor.
- Purging a path removes the file and all nested child paths and `@page-...` variants.
- Purging `/` only removes homepage `index.html` and homepage `@...` query variants.
- Purging a query variant (e.g. `/news/a?page=1`) removes only that variant.
- `purgeMany()` runs batch purges. Successfully deleted URLs are not restored if a subsequent URL errors.
- `purgeAll()` executes only on the release recorded in `control/serving-release`. It moves the live directory to `.<releaseId>.gen-N` and recreates an empty directory in its place without reloading Nginx. Subsequent requests MISS until re-warmed.
- A staged release dirtied by `purgeAll` from the serving release calls `discardGeneration()` to cleanly swap to a fresh generation before `writeCutoverConfig()`.

## 10. Release Deployment & Cutover

Both `root` and `proxy_pass` in the snippet point to the same release. Cutting traffic is an atomic reload:

1. New deployment boots with a new `releaseId` matching its build `deploymentId`.
2. New release calls `init()`. Existing `serving-release` is preserved.
3. Pre-warm high-priority URLs into the new release cache.
4. If the new generation was dirtied by a concurrent `purgeAll`, call `discardGeneration()` and re-warm.
5. Invoke `writeCutoverConfig()` to write the Nginx snippet.
6. Run `nginx -t` and reload Nginx.
7. Call `activateServing(configPath)` to register the new release for subsequent `purgeAll()` calls.

Keep the previous `_next/static` directory configured as `previousStaticRoot` so active browser sessions can load previous chunks.

## 11. TTL & Background Maintenance

- `ttl.seconds` records expiration timestamps in the journal during warming. Nginx continues serving HITs until the background maintenance task cleans them up.
- `startCron()` runs when `cron.enabled: true`, `NEXT_RUNTIME === 'nodejs'`, and `NODE_ENV === 'production'`. Maintenance runs in bounded batches respecting `maxItems` and `maxDurationMs`.
- System crontab can invoke the standalone CLI:

```bash
npx hiden-html-cache-gc \
  --directory /var/cache/hiden \
  --release build-41 \
  --max-items 1000 \
  --max-duration-ms 2000
```

- `clearExpired()` and `cleanupOrphans()` can also be called directly for programmatic garbage collection.

## 12. Verification & Monitoring

- The `X-HTML-Cache` header returns `HIT`, `MISS`, or `BYPASS`.
- Document responses set `Cache-Control` from `document.cacheControl`. Static assets and RSC payloads retain their own cache headers.
- Inspect cache status programmatically:

```ts
const page = await cache.status('/news/article-a');
// state: 'hit' | 'miss' | 'expired' | 'excluded' | 'error'
```

- Custom Nginx log format outside the snippet:

```nginx
log_format hiden '$remote_addr "$request" $status $html_cache_status cookie=$html_cache_cookie_bypass query_ok=$html_cache_query_ok';
```

- `summarizeAccessLog(logText)` counts HIT, MISS, and BYPASS lines. Cookie values are never logged.

Directory structure on disk:

```text
/var/cache/hiden/build-41/index.html
/var/cache/hiden/build-41/news/article-a/index.html
/var/cache/hiden/build-41/news/article-a/@page-1/index.html
/var/cache/hiden/control/
```

`control/` stores coordination state, fences, and locks for Node. Nginx never exposes or reads this directory as a root.

## 13. Cache HIT Conditions

A request produces a cache HIT only when all of the following hold simultaneously:
- Method is `GET` or `HEAD`
- Path is included, not excluded, and has no trailing slash
- Query string is empty or matches an allowed parameter rule
- No cookies and no `Authorization` header
- Not an App Router internal request (no `_rsc` query, no `RSC`, `Next-Action`, `Next-Router-State-Tree`, `Next-Router-Prefetch`, `Next-Router-Segment-Prefetch`, `Next-Url`, `x-nextjs-data`, or `Accept: text/x-component`)
- If `Sec-Fetch-Dest` is present, value is `document`
- The `index.html` file exists on disk for that exact path/query variant

Trailing slash requests receive a redirect to the non-slash path and are never cached. Paths containing `..`, double slashes, or unusual percent-encodings bypass cache.

## 14. Error Handling

Catch `CacheError`. The `error.code` property indicates the failure reason:

| Code | Meaning |
|---|---|
| `POLICY_REJECTED` | Disallowed URL, query, cookie, runtime, or configuration |
| `REVISION_REQUIRED` | An existing revision floor requires `expectedRevision` |
| `REVISION_MISMATCH` | Expected revision or HTML marker does not match stored revision |
| `STALE_EVENT` | `commitVersion` is older than existing revision floor |
| `VERSION_CONFLICT` | Same `commitVersion` provided with a different revision string |
| `RELEASE_MISMATCH` | Release marker in HTML does not match `storage.releaseId` |
| `SUPERSEDED` | A concurrent purge occurred while warming was in-flight |
| `INVALID_RESPONSE` | Origin returned a status, header, or body that fails cache validation |
| `ORIGIN_TIMEOUT` | Origin fetch exceeded `warm.timeoutMs` |
| `FILESYSTEM` | Filesystem error, lock timeout, or uninitialized cache directory |
| `COOLDOWN` | URL is in temporary cooldown following an origin error |

`ConfigError` is thrown synchronously by `createCache()` before any disk I/O occurs.
